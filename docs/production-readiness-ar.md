# تجهيز المنصة للإطلاق

هذه الوثيقة تلخص البنية الفعلية للمشروع وما يلزم شراؤه أو إعداده قبل نشره. المنصة ليست موقعًا ثابتًا أو WordPress؛ إنها تطبيق Next.js يحتاج خادم Node.js وقاعدة PostgreSQL وخدمة تخزين ملفات.

## ما الذي يجب شراؤه؟

1. **اسم نطاق باسم النادي**، ويكون تسجيله وحساب إدارته باسم النادي أو ممثله المعتمد. يمكن شراء النطاق منفصلًا عن الخادم.
2. **استضافة تدعم تطبيق Node.js دائمًا**، إصدار Node.js ‏22.12 أو أحدث، وأوامر `npm ci` و`npm run build` و`npm run start`، وإعداد متغيرات البيئة وإعادة تشغيل التطبيق عبر PM2 أو آلية مكافئة.
3. **قاعدة PostgreSQL إنتاجية مستقلة**. يتصل المشروع بـ PostgreSQL عبر Prisma ويطبق تغييرات قاعدة البيانات من ملفات migrations؛ قاعدة MySQL وحدها لا تكفي.
4. **تخزين كائنات متوافق مع S3** بوعاءين منفصلين: واحد خاص للوثائق، وآخر للصور والوسائط العامة. تخزين الملفات المحلي مناسب للتطوير فقط.
5. **نسخ احتياطية قابلة للاستعادة** لقاعدة البيانات والوعاء الخاص والوسائط. يجب تجربة الاستعادة قبل اعتماد الإطلاق.

قد توفر خطة الاستضافة الشهادة TLS، لكن تحقّق من أنها تشمل تجديدًا تلقائيًا للنطاقين `example.dz` و`www.example.dz`، وإمكانية ضبط DNS وتوجيه HTTPS إلى تطبيق Node.

## سؤال ترسله إلى DZHOSTER قبل الدفع

> لدي تطبيق نادٍ مبني بـ Next.js 15 وNode.js ‏22.12+ وPrisma/PostgreSQL. هل تدعم خطة الاستضافة تشغيل تطبيق Next.js ديناميكي بشكل دائم خلف Nginx، وتشغيل `npm ci` و`npm run build` و`npm run start`، ومتغيرات البيئة وإعادة التشغيل بعد النشر؟ وهل توفر PostgreSQL ‏14+ باتصال TLS، وSSH، وذاكرة تكفي لبناء Next.js، ومهمة عامل Node.js مستمرة أو Cron آمن، واتصالًا صادرًا إلى خدمة تخزين S3 خارجية؟ أحتاج حدود الذاكرة والمعالج والاتصالات، سياسة النسخ الاحتياطي والاستعادة، وما إذا كان SSL مجانيًا ومتجددًا تلقائيًا. إذا كانت الخطة المشتركة لا تدعم ذلك، أحتاج عرض VPS مُدار مع هذه المواصفات.

صفحة الخطط العامة لدى DZHOSTER تعرض استضافة مشتركة مع cPanel وقواعد MySQL. لم أجد فيها تأكيدًا صريحًا لدعم Node.js الدائم أو PostgreSQL؛ لذلك لا تشترِ خطة مشتركة قبل تأكيد هذه المتطلبات كتابةً. إن لم تتوفر، اطلب **VPS مُدارًا** أو استضافة Node مُدارة. لا تختَر الخطة الأعلى لمجرد مساحة التخزين أو عدد صناديق البريد.

## إعداد الإنتاج المطلوب

- جهّز بيئتين منفصلتين: `staging` للاختبار و`production` لبيانات النادي الحقيقية. إعداد المشروع الحالي وقاعدة الاختبار لا يصلحان وجهة إنتاج.
- أنشئ قاعدة PostgreSQL إنتاجية جديدة، بمستخدم تطبيق محدود الصلاحيات، واتصال TLS. طبّق migrations بالأمر `npm run db:migrate:deploy` بعد نسخة احتياطية، ولا تستخدم `db:push` أو `migrate reset` على الإنتاج.
- أنشئ مفتاحي `AUTH_SECRET` و`CRON_SECRET` عشوائيين وفريدين، وكل مفاتيح OAuth والتخزين وتشفير التكاملات عند تفعيلها. ضعها في لوحة الاستضافة فقط، ولا ترسلها في البريد أو تحفظها في Git.
- اضبط `NEXTAUTH_URL` على عنوان HTTPS النهائي. حدّث Google OAuth Redirect URI وOrigins لتطابق النطاق الجديد قبل تفعيل Gmail.
- اضبط الحاوية الخاصة بحيث لا تسمح بالقراءة العامة، والحاوية العامة للصور فقط. استخدم مفاتيح بأقل صلاحيات، وفعّل التدوير والإصدارات والنسخ الاحتياطي حسب إمكانات المزوّد.
- شغّل عمليتي الويب وعامل المهام كلتيهما، أو وفّر Cron موثوقًا يستدعي مسار معالجة المهام بسر `CRON_SECRET`. تحقق من عدم تشغيل العامل مرتين إن لم يكن ذلك مقصودًا.
- راجع الحسابات والأدوار والبيانات التجريبية، وأوقف أي تكامل غير مجهز. لا تشغّل `db:seed` على قاعدة الإنتاج.
- اختبر تسجيل الدخول، استعادة كلمة المرور/إيقاف المستخدم، الصلاحيات حسب الفريق، رفع وتنزيل وثيقة خاصة، إرسال البريد، العربية والفرنسية، والنسخ والاستعادة على `staging` قبل تحويل DNS.

## قيود إطلاق يجب أن يعرفها الممول

- محدد محاولات الدخول والبحث يخزن العدادات ذريًا في PostgreSQL ويعمل عبر نسخ التطبيق. migration باسم `20261006010000_distributed_rate_limit` يجب تطبيقها على staging ثم الإنتاج قبل تشغيل الإصدار الجديد. اضبط الـ Proxy ليزيل ترويسات عنوان العميل الواردة ويضع عنوانًا موثوقًا بنفسه؛ حد الحساب لا يعتمد على عنوان IP.
- فحص التكامل المحدود للمحدد الذري يعمل بالأمر `npm run test:ratelimit:integration`، ويتأكد من أن اسم قاعدة البيانات يتضمن `test` قبل أن يضيف عدادًا مؤقتًا ويحذفه.
- نسخ الملفات وقاعدة البيانات لا ينفذها التطبيق تلقائيًا؛ يجب إعدادها ومراقبتها لدى مزودي البنية التحتية وإجراء تجربة استعادة.
- التحويل الخادمي إلى PDF اختياري ويتطلب خدمة Gotenberg متاحة على شبكة خاصة. يمكن إبقاؤه غير مهيأ والاكتفاء بالمعاينة والطباعة في البداية.
- ربط Gmail وFAF والذكاء الاصطناعي اختياري؛ لا تفعّلها قبل إعداد الأسرار والموافقات المطلوبة. خدمة FAF ليست مصدر بيانات آليًا جاهزًا من دون نقطة تكامل رسمية مصرح بها.
- تدقيق الاعتماديات بعد المعالجة لم يجد تنبيهات (`npm audit`). ثغرة تعشيق الأقواس في `braces` لم يكن لها إصدار upstream مصحح وقت المعالجة؛ يستخدم المشروع نسخة محلية متوافقة مع حد أقصى 100 مستوى تعشيق. راجع هذا التعديل واستبدله بإصدار upstream مصحح فور نشره.

## بوابة النشر

شغّل من نسخة نظيفة وملف القفل:

```sh
npm ci
npm run db:generate
npx prisma validate
npm run db:migrate:deploy
npm run i18n:check
npm run typecheck
npm run lint
npm run test:all
npm audit --omit=dev --audit-level=moderate
npm run build
```

بعد نجاح الفحوص انشر نسخة البناء، شغّل `npm run start` خلف HTTPS، وتحقق من `/ar` و`/fr` و`/ar/login`، ثم راقب الأخطاء والنسخ الاحتياطية. لا ترفع ملفات `.env` أو `.env.local` أو `.storage` أو قواعد البيانات إلى GitHub.

# دراسة تقنية: إشعارات الأهداف على هاتف المستخدم

**التاريخ:** 14 أكتوبر 2026
**النطاق:** الدراسة التقنية وقرار التنفيذ؛ تفاصيل التهيئة الحية في [دليل التفعيل](match-web-push-rollout-ar.md).

## الخلاصة التنفيذية

الفكرة قابلة للتنفيذ دون تطبيق هاتف أصلي، باستخدام Web Push عبر متصفح الهاتف. يلزم أن يوافق المستخدم صراحةً على الإشعارات، وأن يشترك في فئة/فريق أو مباراة. على iPhone وiPad، يتطلب Web Push أن يضيف المستخدم الموقع إلى الشاشة الرئيسية ويفتحه كتطبيق ويب؛ مجرد فتح الموقع في Safari لا يكفي. توثّق Apple دعم ذلك منذ iOS/iPadOS 16.4.

المنصة تملك بالفعل نموذج `MatchEvent` لتسجيل الهدف وتحديث النتيجة داخل معاملة قاعدة بيانات، ولديها إشعارات داخلية للمستخدمين، لكنها لا تحتوي حاليًا على تسجيل Service Worker أو اشتراك Push للأجهزة. لذلك فهذه إضافة جديدة فوق نظام الأحداث الحالي، وليست مجرد تفعيل إشعارات النظام الموجودة.

**التوصية:** تنفيذ Web Push قياسي، مع اشتراكات أجهزة منفصلة، ونظام إرسال غير متزامن مع إعادة محاولة ومنع التكرار. لا نرسل الإشعار من مسار حفظ الهدف نفسه. بسبب اعتماد الموقع على Cloudflare Workers Free وحد CPU البالغ 10ms للطلب، نحتاج تشغيل الإرسال في Queue consumer مع مراقبة حد CPU، أو استخدام خدمة إرسال خارجية. Cloudflare Queues متاحة على الخطة المجانية، لكن حد CPU للـWorker ما يزال ينطبق على المستهلك؛ يجب قياسه عمليًا قبل اعتماد التنفيذ النهائي.

## ما وجدته في المنصة

- تسجيل الهدف يتم في `addMatchEventAction`، حيث يُنشأ الحدث وتُزاد نتيجة المباراة داخل `db.$transaction`.
- أنواع الأهداف التي تعدّل النتيجة حاليًا هي `GOAL` و`PENALTY_GOAL` و`OWN_GOAL`.
- نموذج `Notification` يخزن إشعارات داخلية مرتبطة بحساب المستخدم، مع صلاحيات نطاق الفئات ومنع التكرار. هذا النظام لا يرسل إشعارًا إلى الهاتف عندما يكون الموقع مغلقًا.
- يوجد نظام مهام خلفية في قاعدة البيانات يعالجه مسار Cron دوري. زمنه غير مناسب وحده لإشعار هدف مباشر، لأنه قد ينتظر دورة المعالجة التالية.
- لا يظهر في الملفات التي فُحصت تسجيل Service Worker أو Push Subscription قائم.

## التصميم المقترح

1. **تسجيل الجهاز:** زر واضح في إعدادات الحساب مثل «تفعيل إشعارات المباريات». يطلب الموقع الإذن بعد ضغط المستخدم فقط، ثم يسجل Service Worker ويطلب Push subscription.
2. **ربط الاشتراك:** يخزن الخادم endpoint ومفاتيح الاشتراك مشفرة/محمية، مع `userId` وبيانات الجهاز وحالة الاشتراك. الجهاز اشتراك مستقل؛ للمستخدم أكثر من هاتف، ويمكنه حذف جهاز أو إيقاف كل الإشعارات.
3. **تفضيلات دقيقة:** يختار المستخدم الفئات التي يتابعها، ويمكن إضافة متابعة مباراة منفردة. لا نرسل للجميع افتراضيًا؛ فصلاحيات المستخدمين الداخلية لا تعني تلقائيًا رغبتهم في تنبيهات الهاتف.
4. **حدث موثوق:** عند حفظ هدف يدوي في مباراة مباشرة، تُنشأ رسالة Outbox داخل المعاملة نفسها التي تحفظ الحدث والنتيجة. الرسالة تحتوي مراجع مثل `matchId` و`eventId` فقط، وليس بيانات حساسة.
5. **إرسال خارج الطلب:** عامل Queue يقرأ الحدث، ويتحقق من أنه هدف جديد في مباراة `LIVE` ومن اشتراك المتابع، ثم يرسل Web Push عبر VAPID إلى خدمة Push الخاصة بالمتصفح. يضع رابطًا مباشرًا لتفاصيل المباراة.
6. **التكرار والتصحيح:** مفتاح فريد من `eventId + subscriptionId` يمنع الإرسال المكرر عند إعادة المحاولة. حذف الهدف/تعديل نوعه لا يرسل إشعار هدف جديدًا تلقائيًا. الاستيراد التاريخي من FAF أو التقرير بعد المباراة لا يرسل إشعارات مباشرة.
7. **التنظيف والتشغيل:** إعادة محاولة أخطاء الشبكة، طابور رسائل فاشلة للمراجعة، حذف الاشتراكات التي يعلن مزود Push انتهاءها، وقياسات لزمن الإرسال ونسبة الفشل وعدد المشتركين.

### محتوى الإشعار

مثال: «هدف لأمل سيدي حسني — 1–0 أمام [اسم الخصم]، الدقيقة 34». لا نضع اسم اللاعب أو بيانات شخصية افتراضيًا؛ يمكن إضافتها كخيار، مع مراعاة خصوصية اللاعبين القُصّر. النقر يفتح صفحة المباراة، مع تحديث النتيجة من الخادم بدل اعتبار محتوى الإشعار مصدرًا موثوقًا للحالة.

## الإيجابيات التقنية

- يصل للمستخدم حتى عندما يكون الموقع مغلقًا أو يعمل في الخلفية، بحسب دعم النظام وإعدادات المستخدم.
- Web Push معيار مشترك بين المتصفحات ولا يتطلب نشر تطبيق Android/iOS أصلي أو دفع رسوم Apple Developer لهذا الغرض.
- يندمج مع حدث الهدف الموجود بالفعل، ويمكن إرسال الإشعار بعد تأكيد المعاملة لضمان عدم إعلان هدف لم يُحفظ.
- لا يحتاج إرسال تنبيه واحد إلى polling مستمر من الهاتف؛ وهذا أقل استهلاكًا للبطارية والطلبات من إبقاء اتصال حي مفتوح.
- Queue وOutbox يعزلان إرسال الإشعارات عن حفظ الهدف، فيستمر التسجيل حتى لو تعطل مزود Push، ثم تتم إعادة المحاولة.
- يمكن للمستخدم ضبط تفضيلاته حسب الفئة أو المباراة وتعطيل الجهاز بسهولة.

## السلبيات والمخاطر

- **الإذن ليس مضمونًا:** المستخدم قد يرفض الطلب أو يعطله من إعدادات النظام. يجب ألا نطلب الإذن تلقائيًا عند أول زيارة؛ ينبغي أن يكون بعد اختيار واضح من المستخدم.
- **قيد iPhone:** على iOS/iPadOS يجب إضافة الموقع للشاشة الرئيسية، وقد تكون هذه الخطوة مربكة لبعض المستخدمين. يجب أن تعرض المنصة تعليمات قبل زر التفعيل.
- **التسليم ليس لحظيًا مضمونًا:** شبكات Push وأنظمة توفير الطاقة ووضع التركيز قد تؤخر التنبيه أو تخفيه. الإشعار قناة تنبيه، وليس مصدر الحقيقة أو ضمانًا زمنيًا.
- **تعقيد تشغيلي:** مفاتيح VAPID، endpoint لكل جهاز، انتهاء الاشتراكات، retries، رسائل فاشلة، مراقبة، وتحديثات Service Worker.
- **تكرار أو إشعار خاطئ:** قد تعيد Queue المحاولة، وقد يصحح المسجل هدفًا لاحقًا. يلزم منع تكرار دائم وسلوك واضح للتعديلات، وعدم إرسال أهداف التقرير التاريخي كأنها مباشرة.
- **خصوصية:** endpoint ومفاتيح الاشتراك بيانات مرتبطة بجهاز المستخدم؛ يجب حماية الوصول لها، وتوفير إلغاء الاشتراك والحذف، وعدم تضمين تفاصيل زائدة في شاشة القفل.
- **المتصفح يملك القرار النهائي:** إلغاء الإذن أو حذف الموقع/بياناته أو تغيّر الجهاز ينهي الاشتراك. لا توجد طريقة موثوقة لإجبار التنبيهات على الوصول.
- **مخاطر الأداء الحالية:** الخطة المجانية لـWorkers تحد CPU لطلب HTTP إلى 10ms وفق وثائق Cloudflare. تشفير Push وتصفية المستلمين ضمن طلب حفظ الهدف قد يزيد الحمل ويعيد خطر 1102؛ لهذا يجب الإرسال خارج المسار الحرج وعدم استدعاء خدمة خارجية قبل تثبيت الهدف.
- **توسيع النطاق:** إذا كان المقصود مستقبلًا تطبيقًا أصليًا أو تنبيهات SMS/WhatsApp، فهذه قنوات مختلفة، وتحتاج تكاملًا وتكاليف وسياسات إضافية.

## خطة تنفيذ مرحلية مقترحة

1. تأكيد الجمهور: مشجع عام يتابع فئة، أم مستخدم مسجل، أم كلاهما. الأفضل السماح بالاثنين مع تفضيلات مستقلة.
2. إضافة manifest وService Worker وواجهة تفعيل/إلغاء اشتراك، مع رسائل إرشاد واضحة لمستخدمي iPhone.
3. إضافة جدول اشتراكات للأجهزة وجدول تفضيلات/Outbox مع فهارس ومفاتيح idempotency.
4. ربط إنشاء Outbox بهدف يدوي جديد في مباراة مباشرة ضمن معاملة الحدث والنتيجة، وفق قواعد معلنة للهدف العكسي والتقارير المتأخرة والتعديلات.
5. إرسال عبر Cloudflare Queue consumer أو خدمة خارجية، مع retries وDLQ وحذف endpoint المنتهي. عدم استخدام Cron كل دقيقة لإرسال تنبيه مباشر.
6. اختبار الأجهزة الفعلية: Android Chrome، iPhone مع إضافة الشاشة الرئيسية، Safari/macOS، رفض الإذن، جهازين لحساب واحد، قطع الشبكة، إعادة المحاولة، الهدف العكسي، تعديل/حذف الهدف، والاستيراد التاريخي.
7. طرح تجريبي لمجموعة صغيرة، ثم مراقبة زمن الوصول ونسبة الفشل وإلغاء الاشتراك قبل تعميمه.

## قرار تقني مقترح

اعتماد **Web Push عبر معيار Push API + Service Worker** كقناة أولى، مع **اشتراك اختياري لكل جهاز** و**اختيار فريق/فئة للمتابعة**، و**Outbox + Queue** للإرسال. لا نرسل لجميع زوار الموقع تلقائيًا، ولا نعتمد على قاعدة البيانات الدورية الحالية للإرسال العاجل. يجب التحقق بقياس صغير من توافق تشفير مكتبة الإرسال مع Cloudflare Workers وحد CPU الحالي قبل اختيار تنفيذ الإرسال النهائي.

## حالة التنفيذ بعد موافقة المستخدم

أضيفت واجهة تفعيل عامة وإلغاء اشتراك الجهاز، وService Worker، ومفاتيح VAPID للإعداد، وجداول الاشتراك والفئات وسجل التسليم وOutbox. تسجيل الأهداف وتحديث النتيجة وإضافة رسالة إشعار الهدف يتم داخل المعاملة نفسها. كما أضيفت رسائل لبداية المباراة ونهايتها عند تحديث الحالة، وبداية المباريات المجدولة عبر Cron، وطابور Cloudflare لإرسال منفصل.

التنفيذ البرمجي وحده لا يفعّل الموقع الحي. يلزم إعداد المفاتيح والطوابير وتطبيق migration ثم النشر؛ لا تُرسل الواجهة إلى مزود Push حتى تتوفر المفاتيح. بداية المباراة المجدولة مرتبطة بدورة Cron الحالية كل دقيقة، وقد يتأخر التنبيه حتى 60 ثانية. كما ينبغي مراقبة CPU في أول إرسال فعلي لأن تشفير Web Push يظل خاضعًا لحدود Worker.
